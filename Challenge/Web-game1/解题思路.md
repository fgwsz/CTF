## 第四次攻击:超大`score`
重新看一个这个网络请求:
```js
var sign = Base64.encode(score.toString()); # sign是base64(score)
xmlhttp.open("GET","score.php?score="+score+"&ip="+ppp+"&sign="+sign,true);
```
但是我们分数300的时候,给后端服务器发动的请求是:
```
/score.php?score=300&ip=104.28.158.225&sign=zMMzAw==
```
使用`base64_tool.py`检查一下`sign`是否是正确的`base64(300)`正确:
```bash
$ python3 ../../Tools/Crypto-base64_tool/base64_tool.py -e "300"
MzAw
$ python3 ../../Tools/Crypto-base64_tool/base64_tool.py -d "MzAw"
300
$ python3 ../../Tools/Crypto-base64_tool/base64_tool.py -d "zMMzAw=="
[提示] 解码结果不是有效 UTF-8 文本，已转十六进制显示
ccc33303
```
这样看来就发现了一件事`index`里面使用的`Base64.encode()`函数是自定义的函数,
并不是标准的`Base64解码器`.

`300`->`base64(300)->``MzAw`->`magic_func("MzAw")`->`zM{MzAw}==`

它可能使用了上述的转换规则:
1. 头部添加`zM`前缀
2. 尾部补充`==`后缀

那既然得分是`300`返回响应:失败了,那么我们构建一个超大的得分`GET`请求,
看一下会发生什么呢?会成功吗?成功后会返回`flag`吗?
首先选取分数为`999999999`(9个9),足够大了.
```bash
$ python3 ../../Tools/Crypto-base64_tool/base64_tool.py -e "999999999"
OTk5OTk5OTk5
```
得到`base64(999999999)=OTk5OTk5OTk5`

根据自定义`Base64`转换原则,添加`zM`前缀和`==`后缀.

然后直接地址栏访问:
```
http://160.202.254.160:13088/score.php?score=999999999&ip=104.28.158.225&sign=zMOTk5OTk5OTk5==
```
页面显示:
```
flag{2f7c7b6b7230fe34394b34627be0fe23}
```
至此,提交`flag{2f7c7b6b7230fe34394b34627be0fe23}`,发现通过,解题结束.
